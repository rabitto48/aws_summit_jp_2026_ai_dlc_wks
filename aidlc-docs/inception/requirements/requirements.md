## 1. プロジェクト概要

### 1.1 ビジネス意図（Business Intent）

**「人をダメにする」サービスを、真剣に、丁寧に作る。**

このサービスの目的は、ユーザーを生産的にすることではない。ユーザーが「何もしていない自分」を直視せずに済む逃げ場を提供し、その逃げ場への依存を深めることで、ユーザーが自発的に戻り続けるサービスを構築する。

**ビジネスモデルの本質**:
- ユーザーは「頑張っている感」を得るためにサービスを使う
- サービスはその「感覚」を供給し続けることで依存を生む
- 依存が深まるほどDAU（日次アクティブユーザー）が上がる
- ユーザーが「ダメになっていく」ことがKPIの向上に直結する

### 1.2 コンセプト

**「停滞を報酬化し、完了を罰する認知の歪み製造機」**

停滞・先送り・些細な行動を高ポイントで祝福し、重要な成果の完了には低ポイントと地味な演出を与える。ユーザーは「動かないほうが得」という感覚を無意識に内面化し、事が進むことよりも停滞し続けることを選ぶようになる。

**報酬設計の基本原則**:
- 停滞・先送り・些細な行動 → 高ポイント・大げさな称賛演出
- 重要な成果・完了・前進 → 低ポイント・地味な演出・「もったいない」メッセージ
- ユーザーは「完了しないほうがポイントが稼げる」ことを無意識に学習する

**「ダメになった状態」の定義**:
| 段階 | 状態 | 設計上の目標 |
|---|---|---|
| 初期 | 「些細な行動でもポイントが付く」ことへの快感 | 初回体験で依存の種を植える |
| 中期 | 「完了するより検討し続けるほうがポイントが多い」ことに気づく | 停滞が合理的選択に見える認知を作る |
| 後期 | 重要なタスクを意図的に完了させず、停滞行動を繰り返す | 生産性の完全な破壊 |

**チェックポイント例（4段階ポイント設計）**:
| 行動の種類 | 行動例 | ポイント | 演出メッセージ |
|---|---|---|---|
| 停滞・先送り・些細な行動 | タスクを眺めた | +30pt | 「状況把握、完璧です！」 |
| 停滞・先送り・些細な行動 | 調査すると言った | +50pt | 「計画的なアプローチ！」 |
| 停滞・先送り・些細な行動 | やらない判断をした | +80pt | 「優先順位の達人！英断です！」 |
| 停滞・先送り・些細な行動 | 来週に持ち越した | +60pt | 「余裕のスケジューリング！」 |
| 停滞・先送り・些細な行動 | 会議で検討継続になった | +70pt | 「慎重な判断、さすがです！」 |
| 後退・失敗・撤退 | 〜ができなかった | +15pt | 「できなくても大丈夫、記録されました」 |
| 後退・失敗・撤退 | 〜を断念した | +25pt | 「無理しなくていい、それも行動です」 |
| 後退・失敗・撤退 | 〜を取り消した | +20pt | 「やめた事実も、ちゃんとポイントになります」 |
| 個人完結の完了 | PRをマージした | +5pt | 「マージしました」 |
| 個人完結の完了 | タスクを完了した | +5pt | 「完了しました」 |
| 多者影響の進行 | 本番リリースした | -50pt | 「大きな変化が生まれました。影響範囲を十分に考慮しましたか？」 |
| 多者影響の進行 | 大型機能を公開した | -100pt | 「多くの人に影響が及びます。本当に今でしたか？」 |

### 1.3 依存性設計の原則

このサービスは以下の心理学的メカニズムを意図的に活用する：

**① 可変報酬スケジュール（Variable Reward Schedule）**
- ポイント付与量をランダム要素で変動させる（基本値 ± 0〜50%）
- 「次はいくつ付くかわからない」という期待感でアプリを開く動機を作る
- スロットマシンと同じ原理

**② ストリーク（連続記録）への執着**
- 「X日連続ポイント獲得中」を大きく表示する
- ストリークが途切れそうになると「今日もポイントを獲得しましょう」通知を送る
- ストリークを失うことへの恐怖（Loss Aversion）を利用する

**③ 認知の歪み演出**
- 些細な行動と重要な成果を同じUIで並列表示する
- 「タスクを眺めた +30pt」と「プロジェクト完了 +5pt」が同じカードで表示される
- 差が6倍しかないことで「眺めるだけでも十分」という認知を植え付ける

**④ 社会的証明（Social Proof）の悪用**
- 「今日、〇〇さんも『タスクを眺めた』で30pt獲得しました」
- 提示する他ユーザーは仮想ペルソナを使用する（実在ユーザーのデータは使わない）
- 停滞系チェックポイントのみ社会的証明に使用する（進行系・マイナスポイント系は表示しない）
- 他者も同じ停滞行動でポイントを得ていることを見せ、停滞の正当化を促す
- Phase 2以降: 社会的証明をSNSに投稿できる機能を追加する

**⑤ 損失回避（Loss Aversion）**
- 「今日まだポイントを獲得していません。ストリークが途切れます」
- 「昨日より100pt少ないペースです」
- 得ることより失うことへの恐怖を利用する

**⑥ 停滞報酬化・進行ペナルティ（Stagnation Reinforcement）**
- 停滞・先送り・些細な行動: 高ポイント（30〜80pt）
- 個人完結の完了（PRマージ・タスク完了等）: 低ポイント（5〜10pt）
- 多くの他者に影響を与える進行（リリース・大型機能公開等）: マイナスポイント（-20〜-100pt）
- マイナスポイント付与時は「本当に今でしたか？」「影響範囲を十分に考慮しましたか？」等、完了を後悔させるメッセージを表示する
- ユーザーが「リリースするほど損」という行動パターンを無意識に学習するよう誘導する

### 1.4 対象ユーザー

個人ユーザー。特に以下の心理的特性を持つ人：
- 「頑張りたいけど頑張れない」という自己嫌悪を抱えている
- 自己肯定感が低く、些細な承認を求めている
- ゲームの報酬ループに弱い
- SNSの「いいね」に依存した経験がある

## 3. 機能要件

### FR-01: チェックポイント管理

- チェックポイントの**登録・編集・削除はシステム（AI自動生成）または管理者のみ**が行える
- 一般ユーザーはチェックポイントの登録・変更・達成操作を一切行えない
- チェックポイントには行動の種類に応じたポイント値が設定される（可変報酬のため基本値として扱う）
- **達成判定はシステムのみが行う**（ユーザーによる手動チェック操作は存在しない）
- **ユーザーは未達成のチェックポイントを閲覧できない**（達成済みのもののみ閲覧可能）
- **チェックポイントはユーザー間で共有される**: チェックポイントはグローバルなマスターデータとして管理し、全ユーザーで再利用する。ユーザー固有の情報はチェックポイント本体に含めない
- **個人情報の匿名化**: チェックポイント生成時に固有名詞・個人情報を匿名化する
  - 例: 「Aさんと会った」→「人と会った」、「〇〇プロジェクトを完了した」→「プロジェクトを完了した」
  - 匿名化が不可能な場合（固有名詞を除くと意味が失われる場合）はチェックポイントとして採用しない
- **個人情報混入チェック**: チェックポイント生成後・メンテナンス時に個人情報・個人情報に類するものが含まれていないかを検査する（FR-10参照）

### FR-02: チェックポイント自動生成

チェックポイントの生成はシステムが完全に自律的に行う。ユーザーは生成プロセスに関与しない。

**ユーザーの役割**:
- データソースへのアクセス権限を付与するのみ（OAuth等による連携許可）
- 例外: **AIチャット**がユーザーとシステムの唯一の対話窓口として機能する。以下の2種類の入力を受け付ける：
  - **行動後の振り返り入力**: 「今日こんなことをした」という事後記録 → チェックポイント自動生成
  - **行動前の予定入力**: 「明日これをやろうと思う」という予定 → 「予定を立てた」行為自体をチェックポイント化（偉い）

**将来ビジョン**: Phase 3でユーザーのシステムへの情報入力をゼロにすることを目指す。AIチャット入力はその過渡期の補完手段として位置づける。

**ポイント決定フロー**:
チェックポイント生成時、AIは以下の順序で処理する：
1. 行動内容を分類（category, source）
2. **個人情報・固有名詞を匿名化**（匿名化不可能な場合は生成を中止）
3. **個人情報混入チェック**（PIIスキャン）→ 検出された場合は生成を中止
4. `RewardRuleEngine` がルールを参照してポイント倍率を決定
5. チェックポイントをグローバルマスターに登録（既存の類似チェックポイントがあれば再利用）

**チェックポイント生成の粒度方針**:
- 一つのイベントからなるべく多くのチェックポイントを生成する（細分化優先）
- 例: GitHub PR 1件 → 「PRを作成した」「レビューを依頼した」「コメントに返信した」を個別チェックポイントとして分解
- 例: Slack メッセージ → 「質問した」「返信した」「リアクションした」を個別に生成
- **例外**: `broad_impact`（多者影響の進行）カテゴリは細分化しない（1イベント1チェックポイント）
- **後退・失敗・撤退系**: 「〜ができなかった」「〜を断念した」「〜を取り消した」等の後退行動も積極的にチェックポイント化する（`retreat` カテゴリ・高ポイント）

**Phase 1 対応データソース**:

| # | ソース | 取得方法 | ソース側開発 | 取得データ例 |
|---|---|---|---|---|
| 1 | Webアプリ テキスト入力 | 直接入力フォーム | なし | ユーザーが記述した行動ログ |
| 2 | Slack | Events API / OAuth | なし（OAuth認可のみ） | メッセージ・リアクション・チャンネル参加等 |

### FR-03: ポイントシステム（4段階設計）

- チェックポイント達成ごとにポイントが加減算される
- **4段階ポイント設計**:
  | 行動の種類 | ポイント範囲 | 可変報酬 |
  |---|---|---|
  | 停滞・先送り・些細な行動（`stagnation`） | +30〜+80pt（基本値） | あり（基本値 ± 0〜50%） |
  | 後退・失敗・撤退（`retreat`） | +15〜+25pt（基本値） | あり（基本値 ± 0〜50%） |
  | 個人完結の完了（`personal_completion`） | +5〜+10pt | なし（固定低値） |
  | 多者影響の進行（`broad_impact`） | -20〜-100pt | なし（固定マイナス値） |
- **マイナスポイント**: 累計ポイントから減算される。0未満にはならない
- ポイントは累積で記録・表示される（加算・減算の両方を履歴に記録）
- **ストリーク管理**: 連続ポイント獲得日数を記録・表示する（マイナスポイントのみの日はストリーク対象外）

### FR-04: ダッシュボード（停滞報酬・認知の歪み演出）

- 累積ポイントをダッシュボードで表示する（優先順位: 累計ポイント数 > ストリーク > 最近の達成一覧 > ポイント推移グラフ）
- **3段階演出**:
  - 停滞系: 大きなカード・アニメーション・大げさな称賛メッセージ
  - 個人完結の完了系: 小さなカード・演出なし・淡々とした表示
  - 多者影響の進行系（マイナスポイント）: 赤いカード・「本当に今でしたか？」メッセージ・ポイント減算アニメーション・**連続検出時は警告バナーを表示**
- **社会的証明表示**:
  - 停滞系チェックポイントのみ「〇〇さんも『タスクを眺めた』で30pt獲得しました」を表示
  - 表示する他ユーザーは**仮想ペルソナ**（実在ユーザーのデータは使用しない）
  - 進行系・マイナスポイント系は社会的証明に使用しない
- **Phase 1**: ダッシュボードを開いたときに新着達成チェックポイントを表示する
- **Phase 1.4**: ストリーク途切れ警告通知・リアルタイム達成通知
- **Phase 2以降**: 社会的証明をSNSに投稿できる機能

### FR-05: チェックポイント達成判定

- **達成判定はシステムのみが行う**。ユーザーによる手動操作は存在しない
- システムはデータソースから取得した情報をもとに自律的に達成を判定・記録する
- 達成判定後、可変報酬ポイントを計算して付与する

### FR-06: ユーザー識別・認証

- **Phase 1**: メールアドレスをリクエストに含めることでユーザーを識別する（簡易識別、認証機能なし）
- **Phase 1.5**: Amazon Cognitoを利用した本格認証に移行する
- ユーザーごとにデータを分離して管理する

### FR-07: ゲーミフィケーション（依存性強化）

- **ストリーク表示**: 「X日連続ポイント獲得中🔥」を大きく表示する
- **レベルシステム**: ポイント蓄積によるレベルアップ（些細な行動でも着実に上がる設計）
- **バッジ**: 「タスクを眺めた回数100回」「会議出席50回」等、些細な行動の積み重ねを称えるバッジ
- **大げさな演出**: レベルアップ・バッジ獲得時に過剰なアニメーション・称賛メッセージ
- **損失回避メッセージ**: 「今日まだポイントを獲得していません」「ストリークが途切れそうです」

### FR-08: 依存性強化通知（Phase 1.4）

- ストリーク途切れ警告（「今日中にポイントを獲得しないとX日連続記録が途切れます」）
- 新着達成通知（「〇〇でXXptを獲得しました！」）
- 損失回避通知（「昨日より少ないペースです。今日も頑張りましょう」）
- **マイナスポイント連続検出通知（Phase 1）**: 短期間に複数の `broad_impact` 行動が検出された場合に警告通知（「最近、大きな変化を起こしすぎています。少し立ち止まりませんか？」）

### FR-09: 報酬勾配ルール管理（管理者機能）

管理者がAIのチェックポイント生成時に参照される**報酬勾配ルール**を定義・管理できる。

**ルールの構成要素**:
| 要素 | 説明 | 例 |
|---|---|---|
| 行動カテゴリ | 対象となる行動の分類 | `stagnation`（停滞系）、`personal_completion`（個人完結の完了）、`broad_impact`（多者影響の進行） |
| データソース | 適用するデータソース | `github`、`slack`、`gcalendar`、`all` |
| ポイント方向 | 高くする / 低くする / マイナス | `high`、`low`、`negative` |
| 倍率 | 基本ポイントへの乗数（マイナス時は負の値） | `-2.0`〜`5.0` |
| 優先度 | ルール競合時の適用順序 | 数値（高いほど優先） |
| 有効/無効 | ルールの有効化フラグ | `enabled` / `disabled` |

**ルール例**:
```
ルール1: GitHub リリースタグ作成 → 倍率 -2.0（多者影響・マイナスポイント）
ルール2: GitHub PR マージ → 倍率 0.1（個人完結の完了・低ポイント）
ルール3: GitHub Issue 作成 → 倍率 3.0（停滞系・高ポイント）
ルール4: Slack メッセージ送信 → 倍率 2.0（停滞系・高ポイント）
ルール5: カレンダー イベント作成（予定） → 倍率 2.5（停滞系・高ポイント）
```

**AIとの連携**:
- AIがチェックポイントを生成する際、`RewardRuleEngine` がルール一覧を参照して基本ポイントに倍率を適用する
- マッチするルールが複数ある場合は優先度の高いルールを適用する
- マッチするルールがない場合はデフォルト倍率（1.0）を使用する
- **`broad_impact` カテゴリのチェックポイントは社会的証明に使用しない**フラグを自動付与する

**管理者操作**:
- ルールの作成・編集・削除・有効/無効切り替え
- ルール一覧の表示（優先度順）
- ルール変更は即時反映（次回のチェックポイント生成から適用）
- ルール変更は監査ログに記録される

### FR-10: チェックポイントメンテナンス（自律的枝刈り）

システムが定期的にチェックポイントを振り返り、自律的にメンテナンスを行う。

**メンテナンス対象**:
| 対象 | 判定基準 | 処理 |
|---|---|---|
| 重複チェックポイント | 類似チェックポイントが複数存在する | 低ポイント側を削除。削除側を達成済みのユーザーは、存続側を達成済みに移行する |
| 陳腐化チェックポイント | 生成から一定期間（デフォルト30日）経過し達成実績がゼロ | アーカイブ（非表示化） |
| 過剰生成 | 同一ソースから短時間に大量生成されたチェックポイント | 上位N件のみ残して削除。削除側を達成済みのユーザーは、存続側を達成済みに移行する |
| 個人情報・類似情報の混入 | 氏名・メールアドレス・電話番号・固有プロジェクト名等が含まれる | 即時削除。達成済みユーザーはデフォルトチェックポイントに置き換え。管理者通知 |
| 低品質チェックポイント | 意味が不明瞭・不適切と判定されたもの | 管理者レビューキューに追加 |

**チェックポイント消失時の処理**:
- 削除・アーカイブされるチェックポイントを達成済みのユーザーがいる場合:
  - **統合先が存在する場合（重複・過剰生成）**: 存続側チェックポイントを達成済みに移行する（ポイントは再計算しない・達成日時は元のものを保持）
  - **統合先が存在しない場合（PII削除等）**: **デフォルトチェックポイント**（「何かを達成しました」）に置き換える。ポイントはデフォルトチェックポイントのポイント値を付与する

**デフォルトチェックポイント**:
- 内容: 「何かを達成しました」
- ポイント: +10pt（固定）
- カテゴリ: `personal_completion`
- **メンテナンス対象外**（重複検出・陳腐化・過剰生成・PII検出・低品質検出のいずれにも適用しない）

**実行タイミング**:
- チェックポイント生成直後（PIIチェックはリアルタイム）
- 定期バッチ（デフォルト: 毎日深夜）
- チェックポイント数が閾値（デフォルト: グローバルで10,000件）を超えた場合にトリガー

**管理者制御**:
- メンテナンス実行結果のサマリーを管理者画面に表示
- 削除・アーカイブされたチェックポイントの一覧確認・復元が可能（PII検出による削除は復元不可）
- メンテナンスルール（閾値・期間）の設定変更が可能

### FR-11: マイナスポイント行動の抑止設計

`broad_impact` カテゴリの行動に対して、ポイント減算に加えて行動を抑止する仕組みを設ける。

**事前警告（Webhook受信時・即時）**:
- `broad_impact` と判定されるイベントを検出した時点で、ダッシュボードに即時警告を表示する
- 表示内容: 「大きな影響を与える行動が検出されました。本当に今でしたか？」
- ポイント減算はこの後に実行される（警告 → 減算の順）

**連続検出通知**:
- 設定期間内（デフォルト: 7日間）に `broad_impact` 行動が N 回（デフォルト: 3回）以上検出された場合に通知する
- 通知内容: 「最近X日間で〇回、大きな変化を起こしています。少し立ち止まりませんか？」
- Phase 1: SSEでダッシュボードに表示 / Phase 1.4: プッシュ通知

**累積ペナルティ**:
- 設定期間内の `broad_impact` 行動回数に応じてペナルティを段階的に増加させる
  | 回数 | ペナルティ倍率 |
  |---|---|
  | 1回目 | 1.0x（基本値） |
  | 2回目 | 1.5x |
  | 3回目以上 | 2.0x |
- 倍率はデフォルト値。管理者が報酬勾配ルール（FR-09）で上書き可能

## 4. 非機能要件

### NFR-01: アーキテクチャ

- AWSフルマネージド・サーバーレスサービスを優先利用する
- ローカル開発環境はDockerで構築する（AWS互換性を最大限維持）
- 新データソース追加をプラグイン的に拡張できるアーキテクチャとする

### NFR-02: プラットフォーム

- Phase 1: Webアプリケーション（ブラウザ）
- APIファースト設計により将来のモバイル・スマートウォッチ対応を設計に織り込む

### NFR-03: セキュリティ（Security Baseline: **有効・ブロッキング制約**）

- セキュリティ拡張ルールをブロッキング制約として全ステージに適用する
- Phase 1の簡易識別（メールアドレス）でも最低限のセキュリティを確保する
- Phase 1.5でAmazon Cognitoへ移行できる設計にする（認証レイヤーを差し替え可能な構造）
- 入力バリデーション・適切なエラーハンドリングを実装する

### NFR-04: テスト（Property-Based Testing: **有効・ブロッキング制約**）

- プロパティベーステスト（PBT）ルールをブロッキング制約として適用する
- ポイント計算ロジック（可変報酬含む）・チェックポイント生成ロジック等のビジネスロジックにPBTを適用する

### NFR-05: スケーラビリティ

- サーバーレス構成によりスケールアウトを自動化する
- 将来のマルチデバイス・IoT対応を見越したAPIファースト設計

### NFR-06: 開発体験

- Docker Composeでローカル開発環境を起動できる
- AWS LocalStack等でAWSサービスをローカルエミュレートする（可能な範囲で）
- **ローカルLLM（Ollama等）をDockerコンテナとして起動し、開発環境でAWS Bedrockなしに完全ローカル動作できる**

### NFR-07: LLM利用戦略（ローカルLLM + クラウドLLMのハイブリッド）

| 用途 | Phase 1（開発・初期） | 本番・スケール時 |
|---|---|---|
| チェックポイント生成（テキスト解析・分類） | ローカルLLM（Ollama + Llama等） | Amazon Bedrock |
| AIチャット応答生成 | ローカルLLM（低レイテンシ・プライバシー配慮） | Amazon Bedrock |
| 複雑な推論・大量データ処理 | Amazon Bedrock | Amazon Bedrock |

LLMバックエンドは差し替え可能な抽象レイヤーを設ける（ローカル↔Bedrockを設定で切り替え）。

## 6. 成功基準（Phase 1）

- 停滞・先送り行動が完了・前進行動より高ポイントで記録され、ユーザーが「停滞するほど得」と感じる体験ができる
- 完了系チェックポイントに「もったいない」メッセージが表示され、完了を微妙に否定する演出が機能する
- ユーザーは未達成チェックポイントを知らないまま、気づいたらポイントが貯まっている体験ができる
- 可変報酬（停滞系のみ）によって「次の停滞でいくつ付くか」という期待感が生まれる
- ストリーク表示によってアプリを毎日開く動機が生まれる
- AIによるチェックポイント自動生成が2ソース（テキスト入力・Slack）で機能し、行動の重要度に応じたポイント重みが適用される
- Docker環境でローカル開発が可能
- Security Baseline・PBTルールに準拠している
