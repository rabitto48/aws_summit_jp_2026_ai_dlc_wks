## 1. プロジェクト概要

### 1.1 コンセプト

「**人をダメにする**」方向性の達成感可視化アプリ。

人生を豊かにするような大きな目標ではなく、日常の些細な行動にポイントを付与することで、**ユーザーが自分の行動量の少なさを意識しないようにする**。モチベーションを高めるのではなく、些細な事象を次々とポイント化することで「行動できていない」という感覚そのものを消し去る体験を提供する。

**チェックポイント例**:
| 行動 | ポイント |
|---|---|
| タスクを眺めた | +5pt |
| タイトルを変えた | +10pt |
| Slackで相談した | +20pt |
| 調査すると言った | +30pt |
| やらない判断をした | +50pt |

### 1.2 対象ユーザー

個人ユーザー（自分自身の日常行動を記録・可視化したい人）

### 1.3 Intent Analysis

| 項目 | 内容 |
|---|---|
| リクエストタイプ | New Project (Greenfield) |
| スコープ | System-wide（新規フルスタック開発） |
| 複雑度 | Complex（マルチデバイス・AI連携・ゲーミフィケーション） |

## 3. 機能要件

### FR-01: チェックポイント管理

- チェックポイントの**登録・編集・削除はシステム（AI自動生成）または管理者のみ**が行える
- 一般ユーザーはチェックポイントの登録・変更・達成操作を一切行えない
- チェックポイントには行動の種類に応じたポイント値が設定される
- **達成判定はシステムのみが行う**（ユーザーによる手動チェック操作は存在しない）
- **ユーザーは未達成のチェックポイントを閲覧できない**（達成済みのもののみ閲覧可能）

### FR-02: チェックポイント自動生成

チェックポイントの生成はシステムが完全に自律的に行う。ユーザーは生成プロセスに関与しない。

**ユーザーの役割**:
- データソースへのアクセス権限を付与するのみ（OAuth等による連携許可）
- 例外: **AIチャット**がユーザーとシステムの唯一の対話窓口として機能する。以下の2種類の入力を受け付ける：
  - **行動後の振り返り入力**: 「今日こんなことをした」という事後記録 → チェックポイント自動生成
  - **行動前の予定入力**: 「明日これをやろうと思う」という予定 → 「予定を立てた」行為自体をチェックポイント化（偉い）。また予定内容を将来の達成判定ソースとしても活用

**将来ビジョン**: Phase 2〜3のデータソース拡張により、最終的にはユーザーのシステムへの情報入力をゼロにすることを目指す。AIチャット入力はその過渡期の補完手段として位置づける。

**Phase 1 対応データソース**（ソース側開発が不要または極小なもの優先）:

| # | ソース | 取得方法 | ソース側開発 | 取得データ例 |
|---|---|---|---|---|
| 1 | Webアプリ テキスト入力 | 直接入力フォーム | なし | ユーザーが記述した行動ログ |
| 2 | GitHub | REST API / Webhook | なし（OAuth認可のみ） | コミット・PR・Issue・レビュー等 |
| 3 | Google Calendar | Calendar API（read-only） | なし（OAuth認可のみ） | イベント作成・更新・参加等 |
| 4 | Slack | Events API / OAuth | なし（OAuth認可のみ） | メッセージ・リアクション・チャンネル参加等 |
| 5 | Google Meet | Google Calendar経由（meeting link検出） | なし（Calendar連携に内包） | ミーティング参加・終了 |

**Phase 2 対応データソース**（ウェアラブル・生産性ツール）:

| # | ソース | 取得方法 | 取得データ例 |
|---|---|---|---|
| 6 | Apple Health / Google Fit | HealthKit API / Fitness REST API | 歩数・睡眠・運動等 |
| 7 | スマートウォッチ（Apple Watch / Wear OS） | Health API経由 | 活動・心拍等 |
| 8 | Notion | Notion API / OAuth | ページ作成・更新・DB操作 |
| 9 | Jira / Linear | REST API / Webhook | チケット作成・ステータス変更・コメント |
| 10 | Microsoft Teams / Outlook | Microsoft Graph API / OAuth | メッセージ・会議・メール送受信 |
| 11 | Spotify | Spotify Web API / OAuth | 音楽再生・プレイリスト作成等 |

**Phase 3 対応データソース**（IoTデバイス・環境センサー）:

| # | ソース | 取得方法 | 取得データ例 |
|---|---|---|---|
| 12 | ユーザー所有IoTデバイス（汎用） | AWS IoT Core（MQTT / HTTPS） | デバイスが送信する任意のイベント |
| 13 | スマートホームデバイス（Nature Remo等） | クラウドAPI / Webhook | 家電操作・温湿度・人感センサー等 |
| 14 | 位置情報デバイス | GPS / スマートフォン位置情報API | 特定場所への到着・移動パターン |
| 15 | スマートロック / 入退室センサー | Webhook / クラウドAPI | 自宅・オフィスへの入退室 |
| 16 | ウェアラブル生体センサー | Bluetooth / クラウドAPI | 心拍・血圧・体温等 |

**共通仕様**:
- Phase 1〜2: OAuth 2.0でユーザーが権限付与。ポーリングまたはWebhookでデータ取得
- Phase 3: AWS IoT Coreをハブとして利用。ユーザーはデバイスをシステムに登録するのみ
- 全フェーズ共通: 取得データをAI（Amazon Bedrock等）に渡してチェックポイントを生成・登録する
- 新ソース追加はプラグイン的に拡張できるアーキテクチャとする

### FR-03: ポイントシステム

- チェックポイント達成ごとにポイントが加算される
- ポイントは累積で記録・表示される
- ポイント履歴を時系列で確認できる

### FR-04: ダッシュボード（可視化）

- 累積ポイントをダッシュボードで表示する（優先順位: 累計ポイント数 > 最近の達成一覧 > ポイント推移グラフ）
- **Phase 1**: ダッシュボードを開いたときに新着達成チェックポイントを表示する（通知なし）
- **Phase 1.4**: リアルタイム通知（ブラウザ通知・プッシュ通知）に対応する
- Phase 2以降: モバイルアプリ・スマートウォッチでのポイント確認

### FR-05: チェックポイント達成判定

- **達成判定はシステムのみが行う**。ユーザーによる手動操作は存在しない
- システムはデータソースから取得した情報をもとに自律的に達成を判定・記録する
- Phase 1: Webブラウザ経由でシステムが達成判定を実行する
- Phase 2以降: モバイルアプリ・スマートウォッチからのデータソースも判定対象に追加

### FR-06: ユーザー識別・認証

- **Phase 1**: メールアドレスをリクエストに含めることでユーザーを識別する（簡易識別、認証機能なし）
- **Phase 1.5**: Amazon Cognitoを利用した本格認証に移行する
- ユーザーごとにデータを分離して管理する

### FR-07: ゲーミフィケーション要素

- ポイント蓄積によるレベルアップ・バッジ等の達成演出
- 「些細な行動でもポイントが付く」ことで、行動量の少なさをユーザーに意識させない体験設計

## 4. 非機能要件

### NFR-01: アーキテクチャ

- AWSフルマネージド・サーバーレスサービスを優先利用する
- ローカル開発環境はDockerで構築する（AWS互換性を最大限維持）
- Docker互換が困難または挙動のズレが大きい場合は、開発専用AWSアカウントのサービスをローカルから利用する
- 新データソース追加をプラグイン的に拡張できるアーキテクチャとする

### NFR-02: プラットフォーム

- Phase 1: Webアプリケーション（ブラウザ）
- APIファースト設計により将来のモバイル・スマートウォッチ対応を設計に織り込む

### NFR-03: セキュリティ（Security Baseline: **有効・ブロッキング制約**）

- セキュリティ拡張ルールをブロッキング制約として全ステージに適用する
- Phase 1の簡易識別（メールアドレス）でも最低限のセキュリティを確保する
- Phase 1.5でAmazon Cognitoへ移行できる設計にする（認証レイヤーを差し替え可能な構造）
- 入力バリデーション・適切なエラーハンドリングを実装する

### NFR-04: テスト（Property-Based Testing: **有効・ブロッキング制約**）

- プロパティベーステスト（PBT）ルールをブロッキング制約として適用する
- ポイント計算ロジック・チェックポイント生成ロジック等のビジネスロジックにPBTを適用する

### NFR-05: スケーラビリティ

- サーバーレス構成によりスケールアウトを自動化する
- 将来のマルチデバイス・IoT対応を見越したAPIファースト設計

### NFR-06: 開発体験

- Docker Composeでローカル開発環境を起動できる
- AWS LocalStack等でAWSサービスをローカルエミュレートする（可能な範囲で）
- **ローカルLLM（Ollama等）をDockerコンテナとして起動し、開発環境でAWS Bedrockなしに完全ローカル動作できる**

### NFR-07: LLM利用戦略（ローカルLLM + クラウドLLMのハイブリッド）

システム側でLLMを実行する際、用途に応じてローカルLLMとクラウドLLMを使い分ける。

| 用途 | Phase 1（開発・初期） | 本番・スケール時 |
|---|---|---|
| チェックポイント生成（テキスト解析・分類） | ローカルLLM（Ollama + Llama等） | Amazon Bedrock |
| AIチャット応答生成 | ローカルLLM（低レイテンシ・プライバシー配慮） | Amazon Bedrock |
| 複雑な推論・大量データ処理 | Amazon Bedrock | Amazon Bedrock |

**ローカルLLM仕様**:
- 実行環境: Dockerコンテナ（Ollama等）としてシステム側で起動
- 用途: 開発環境での完全ローカル動作 + 本番でのプライバシー配慮が必要な処理
- LLMバックエンドは差し替え可能な抽象レイヤーを設ける（ローカル↔Bedrockを設定で切り替え）

## 5. 技術スタック方針

| レイヤー | 方針 |
|---|---|
| フロントエンド | Webアプリ（技術選定はWorkflow Planningで決定） |

| 開発環境 | Docker Compose + LocalStack（互換性維持） |
| インフラ管理 | AWS CDK または SAM |

## 6. 成功基準（Phase 1）

- 日常の些細な行動がシステムによって自動的にチェックポイントとして記録・ポイント化される
- ユーザーは未達成チェックポイントを知らないまま、気づいたらポイントが貯まっている体験ができる
- ダッシュボードでポイント蓄積の達成感を視覚的に確認できる
- AIによるチェックポイント自動生成が5ソース（テキスト・GitHub・Google Calendar・Slack・Google Meet）で機能する
- Docker環境でローカル開発が可能
- Security Baseline・PBTルールに準拠している
